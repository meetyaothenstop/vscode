## 4. 频率与时序结构：本轮从150kHz单速率改为多速率

用户先询问控制频率是否过高、部分代码是否执行不完，以及如何降低频率，并授权修改；还指出此前反复改代码却未先说明频率和执行预算的问题。

| 当前MAIN项目 | 频率/周期 |
| --- | --- |
| PWM载波 | 150kHz，约6.667μs；HRTIM周期32000ticks |
| ADC触发与快速软件保护 | 150kHz |
| 电流环计算 | 50kHz，20μs，每3个PWM周期请求一次 |
| 电压环计算 | 10kHz，100μs，每5次电流更新一次 |
| CPU/HCLK | 150MHz；每PWM周期1000CPU时钟 |

快速HRTIM_TIMB IRQ优先级0，负责新鲜ADC原码、快速保护、状态和两桥比较值提交。计算在可被抢占的PendSV worker（优先级15），OLED DMA/I2C IRQ为3。未引入RTOS。
PI积分/反馈滤波按20μs/100μs重新离散化，连续PI增益保持；低占空比用逐PWM周期的最小/空脉冲密度调制，避免三周期脉冲成组。
RAW1之后健康快速路径用整数ADC区间与Q24累加，浮点换算/计算在worker或故障冷路径；实际链接指令检查无快速健康路径FP指令，但仍需实板测完整异常开销和最坏时序。

**64 T7**是多速率请求在下一次50kHz请求前仍未完成/发布的截止期保护。可能涉及worker计算、等待和抢占，不等于只量到了PI纯运算。曾有T7现场：elapsed3435周期约22.90μs、spacing1000、counter15968；完成请求峰值2903周期约19.35μs。不能将历史isr_cycles_max单独当作稳定CPU占用率。
30个完整自举周期、2个装载等待周期及Boost交接全关断要求仍保留，未因诊断版本放宽T1～T7或电气门限。

## 5. 当前代码的相关故障码与门限

代码是位掩码；`0x10`是十进制16。首故障包只锁存第一次，`power_status.fault`还可能OR入后续位，因此要同时看`power_event.fault.code`。

| fault | 含义与当前条件 |
| --- | --- |
| 1 | ADC有效性：ADC1缺JEOS或有JQOVF；需要晚相位样本的正向Buck还检查ADC2 EOC/EOS完整且无OVR |
| 2 | 输入条件不满足 |
| 4 | 输出过压；MAIN Buck门限为min(max(最终目标×1.5,6V),40V)，6V目标即计算输出>9V |
| 8 | 采样绝对过流/电流ADC近轨；主工程绝对过流线7.5A |
| 16 | 电流方向保护；反向模式计算IL>+1A连续16个150kHz样本（约106.7μs）；正向IL<−1A立即触发 |
| 32 | 控制器异常 |
| 64 | 时序保护，结合detail T1～T7 |
| 128 | 启动拒绝/复查，结合S编号，不能与fault4等混读 |

反向软件电流预期为负（正方向约定左→右）。实际采样极性、增益和波形尚需已知电流/实板测量确认。
MAIN Buck输入10～42V、非零目标≤实际输入×0.95，冷启动电流绝对值<1A、输出残压≤3V；0V请求是关断，不是主动稳0V，也不清首故障。保护值是软件判据，不是实际峰值保证。

### 8.2 ADG1的启动报1：已定位直接分支，物理原因未确认

有效首包：valid1、code1、detail1、state1=BOOTSTRAP、mode3、run_id1、start_pending0、bootstrap_resume0、自举剩余30、装载0；目标6V，duty/reference/比较值记录0。

补充截图：`adc1_entry_flags=0x1`、`adc2_entry_flags=0xF`、`adc_reason=1`。用户确认上电持续运行、只按板上START，没有暂停/单步后继续。

- ADC1的0x1仅ADRDY，JEOC/JEOS/JQOVF都0。
- ADC2的0xF含ADRDY/EOSMP/EOC/EOS，OVR为0。
- reason1确定“ADC1入口JEOS缺失”，不是已经证明ADC没收到触发。标志也可能此前已被读取/清除；读取JDR能清JEOC，不能据此说会清JEOS。

reason编码：1缺JEOS，2有JQOVF，3两者同时，4正向Buck需要的ADC2延后样本无效。反向不因未使用的ADC2样本无效而报1。首故障为非ADC时，三个ADC专用字段按设计为0。

### 8.3 ADG2要验证的“前一次IRQ迟到”假设

真实后端夹具中人工注入：前一次STOP/待启动IRQ晚至CPU周期相位750（HRTIM计数24000）时，可能读走本周期已完成的ADC1并清JEOS，然后开始自举；下一正常IRQ在相位20到来，仅相隔270CPU周期，此时新ADC1序列尚未发生，ADC2晚相位样本已有完成标志。
此构造能复现code1/reason1、ADC标志1/F、自举剩余30、PI步数0；正常相位对照无ADC故障。**这是合成时序，不是实板迟到已经被测出的证据。** 测试已保存为`tests/adc_bootstrap_phase_test.c`，该exe预包含`tests/adc_real_isr_flags.h`使用真实ISR掩码。

链接反汇编还确认`event_run_start()`在启动提交PRIMASK锁内清零/复制两份172字节事件邮箱。它是待测延迟来源之一，实板耗时未知，尚未移出锁或改启动资格；不能宣称已找到根因。
ADG2只让ADC故障分支把已读取的begin/spacing/counter传入原首故障记录，不增加正常IRQ硬件读探针；先关断再建包：

```text
power_status.fault_spacing_cycles  # 原IRQ入口间隔
power_status.fault_counter_ticks   # 原入口计数器读数
power_status.fault_elapsed_cycles  # 关断之后、故障包复制之前的elapsed
```

elapsed含冷故障分支开销，不能当健康IRQ耗时。正常周期1000CPU时钟，明显短间隔加周期前段的counter支持上一IRQ迟到方向；仍须结合实板数据。DWT和counter读取不是同一条指令时刻，不做无误差相位反算。**当前未取得新的有效ADG2报1入口时序包。**
